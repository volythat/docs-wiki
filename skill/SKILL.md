# docs-wiki

> **Direct operational commands — do NOT run brainstorming first.** When the user says any command from the table below, execute immediately. This is not creative work.

Single-source-of-truth documentation system for app projects. Every fact (term, field, flow, endpoint) is defined in exactly ONE place in `_sources/` (or a `.bru` file in `<dirs.bruno>`); everywhere else only LINKS to it.

## Project config (.docswiki.yml) — read BEFORE every command

**Step 0 (before every command):** read `.docswiki.yml` at cwd (root folder).
- Present → merge with defaults (shallow merge per leaf key); unknown keys ignored.
- Absent → use all defaults, do NOT block execution.
- Also read `.docswiki` (no extension) if present, treat as YAML; `.docswiki.yml` takes precedence.

All paths/conventions below come FROM config, never hardcoded. Defaults: `docs_dir: docs`;
`dirs: {sources: _sources, bruno: api/bruno}`; `lang: {anchor: en, content: vi}`;
`bruno: {base_url: http://localhost:3000, env: local}`; `ignore: []`. Full schema: `references/config.md`.
Below, `<docs_dir>`, `<dirs.sources>`… are values resolved from config.

## Commands

| User says | Action |
|---|---|
| "khởi tạo docs" / "init docs" / "initialize docs" | **Pre-check:** if cwd has no `.docswiki.yml` AND the `docs` folder already exists → STOP, warn of overwrite risk, offer two options: (A) create `.docswiki.yml` with a different `docs_dir` first (e.g. `docs-v2`) then re-run, or (B) confirm scaffolding into current folder (existing files won't be overwritten but new files will be added). Only proceed after user chooses. If `.docswiki.yml` already exists: copy `templates/` into `<docs_dir>`, do NOT overwrite existing files. If cwd has no `.docswiki.yml` and user confirms (B): also generate `.docswiki.yml` at the same time. Report files created. After copying: if `project.name` is non-empty in config, replace the placeholder heading `# Tài liệu dự án` in `<docs_dir>/README.md` with `# <project.name>`. |
| "thêm/sửa thuật ngữ\|field\|endpoint\|flow X" / "add/edit term\|field\|endpoint\|flow X" | Write definition to `<dirs.sources>` (or a `.bru` file in `<dirs.bruno>` for endpoints, per `references/bruno-contract.md`), anchor per `lang.anchor`, content per `lang.content`, conventions in `references/reference-conventions.md`; suggest where to link. After writing: for terms, fields, and flows — always create or update `<dirs.sources>/INDEX.md` using format `- [Anchor name](file.md#anchor) — first sentence, max 10 words`, grouped under a `## <filename>` section (create the section if missing; if INDEX.md does not exist yet, create the file with the section and entry). For endpoints (.bru files): skip INDEX.md — endpoints are indexed by file path, not anchor. |
| "xóa thuật ngữ\|field\|endpoint\|flow X" / "remove/delete term\|field\|endpoint\|flow X" | Safe removal — never delete blindly. (1) Run "where is X used" first: grep links to X's anchor (or `.bru` path) in `<docs_dir>`. (2) Links exist → list file + line, ask user how to handle each (update or remove) BEFORE touching the definition. (3) Only when no incoming links remain → delete the definition block from `<dirs.sources>` (heading + content; for a field also its `<a id>` row). For endpoints, offer deprecate-instead-of-delete first: add `> **DEPRECATED**` as the first line of the `.bru` `docs` block and keep the file; only delete the `.bru` file if user explicitly confirms. (4) Remove the INDEX.md entry if INDEX.md exists. (5) Suggest running "kiểm tra nhất quán" after. **Exception:** `<dirs.sources>/decisions.md` is append-only — never delete a decision; write a superseding ADR instead (see "add/edit decision"). |
| "thêm/sửa quyết định X" / "add/edit decision X" | Write architecture decision to `<dirs.sources>/decisions.md` in minimal ADR format: **Context** (background/problem), **Decision** (chosen solution), **Consequences** (trade-offs). Anchor = English slug describing the decision (e.g. `use-uuid-for-id`). Append if new, update if already exists. If the decision supersedes an old one: add "Supersedes: [old-name](#old-anchor)" and update the old decision with "Superseded by: [new-name](#new-anchor)". ADR is append-only — NEVER delete old decisions, only mark superseded. After writing: always create or update `<dirs.sources>/INDEX.md` using format `- [Anchor name](decisions.md#anchor) — first sentence, max 10 words`, under a `## decisions.md` section (create if missing; create the file if it does not exist yet) — add only a NEW entry for the newly created anchor; NEVER modify entries for old superseded anchors. |
| "thêm file docs [tên]" / "add docs file [name]" / "new docs file [name]" | Ask doc type before creating: **(R) Reference** — technical facts (fields, endpoints, config); **(H) How-to** — step-by-step guide for an already competent user; **(E) Explanation** — rationale, trade-offs, design context. If type cannot be determined → default to **(R) Reference**. Generate appropriate template header per type (Reference: table/list facts + source links; How-to: numbered steps + prerequisites; Explanation: prose + link to decisions.md if relevant). Then create `<docs_dir>/[name].md` linking to `<dirs.sources>/` (DO NOT copy definitions). If related entities/terms are undefined in `<dirs.sources>`, ask user if they want to add them first. After creating, "update TOC" will pick up this file automatically (scan-based, no manual registration needed). Then scan the new file for bold phrases (`**...**`) that have no adjacent `_sources/` link — for each candidate, check if a matching anchor exists in `_sources/` (fuzzy match on slug); list unmatched ones and ask user if they want to add definitions now. |
| "phân tích docs cũ từ [folder]" / "analyze old docs from [folder]" | **Pre-check:** if `<docs_dir>` matches `[folder]` → STOP, require different `docs_dir` in `.docswiki.yml`. `[folder]` is READ-ONLY, never modified or overwritten. **Phase 1 — Analysis:** Read all files in `[folder]`. Classify each content block as: (A) *Source definitions* (terms, entities, fields, flows, architecture decisions) → will go into `<dirs.sources>/glossary.md`, `data-model.md`, or `flows.md`; (B) *Feature summaries/specs* → will become derived docs, propose grouping into domain subfolders (e.g. `features/`, `monetization/`, `content/`); (C) *Endpoints/API* → will go into `.bru` files under `<dirs.bruno>` (per `references/bruno-contract.md`); (D) *Unclear* → list separately. Output report: classification list + proposed folder tree for `<docs_dir>`. Ask for confirmation or adjustments before doing anything. **Phase 2 — Execute:** Only after confirmation: (1) create `<dirs.sources>/` with extracted source definitions — each definition appears here only, NEVER copied elsewhere; (2) create derived files in proposed subfolders — each file may ONLY contain links to `<dirs.sources>/` and short descriptions, NEVER repeat definitions inline; use relative paths that account for subfolder depth (e.g. a file in `features/` must link as `../_sources/glossary.md#term`, not `_sources/glossary.md#term`); (3) create `.bru` files under `<dirs.bruno>` if endpoints exist; (4) create `<dirs.sources>/INDEX.md` from all definitions just written, using the same logic as "tạo index tìm kiếm". NEVER touch `[folder]` at any step. |
| "tái cấu trúc docs" / "restructure docs" | Reshape current `<docs_dir>` to meet docs-wiki standards — do NOT delete and rebuild from scratch. **Mandatory exception:** `<dirs.sources>/decisions.md` is append-only — never restructure, move, or extract content from this file at any step. **Phase 1 — Audit:** Read all files in `<docs_dir>`, identify: (A) definition content sitting inline in derived docs → needs moving to `<dirs.sources>/`; (B) files not grouped into domain subfolders; (C) files already compliant (links only). Output "what needs fixing where" report + proposed folder tree after restructuring. Ask for confirmation. **Phase 2 — Execute (step-by-step, without breaking links):** (1) Extract definitions from derived docs → write to `<dirs.sources>/` with correct anchors; (2) Replace extracted content with links to corresponding anchors; (3) Move files to proposed subfolders; update all links pointing to those files (incoming); also update outgoing links FROM each moved file — adjust relative paths to `<dirs.sources>/` based on new depth (e.g. a file moved into a subfolder must use `../_sources/` instead of `_sources/`); (4) Report each change made. Never delete a file without separate confirmation. After Phase 2 completes: rebuild `<dirs.sources>/INDEX.md` in full using the same logic as "tạo index tìm kiếm" — anchors and paths may have changed. |
| "sinh bruno" / "generate bruno" | Per `references/bruno-contract.md`: scaffold a new `.bru` endpoint skeleton in `<dirs.bruno>` (meta + method/url + headers + body + `docs` block) for the user to fill in. If `<dirs.bruno>` has no `bruno.json` or `environments/<bruno.env>.bru` yet, create them first (`baseUrl` from `bruno.base_url`). `.bru` files are hand-authored source — never overwrite an existing endpoint without confirmation. |
| "kiểm tra nhất quán" / "check consistency" | Per `references/consistency-check.md`: scan `<docs_dir>`, output report. Run ONLY when requested. |
| "thống kê docs" / "docs stats" | Scan and report — no file writes. First read `ignore` array from config and skip matching files/folders throughout. (1) **Source counts** — terms (`### ` in glossary.md), entities (`### ` in data-model.md), fields (`<a id>` in data-model.md), flows (`### ` in flows.md), decisions (`### ` in decisions.md); skip INDEX.md. (2) **Endpoints** — count `.bru` files in `<dirs.bruno>`, skip `bruno.json` and `environments/`. (3) **Derived docs** — count `.md` files in `<docs_dir>` outside `<dirs.sources>/`, exclude `README.md`. (4) **Coverage** — percentage of `_sources/` anchors linked from at least one derived doc (skip INDEX.md links, per consistency-check.md Type 5). Output as a summary table. |
| "X dùng ở đâu" / "where is X used" | Grep all links pointing to X's anchor in `<docs_dir>`; list file + line. |
| "tạo index tìm kiếm" / "create search index" | Scan all headings (anchors) in `<dirs.sources>/` files — skip `INDEX.md` itself. For each anchor, take the first sentence below it as a short description (max 10 words). Generate/overwrite `<dirs.sources>/INDEX.md` with format: `- [Anchor name](file.md#anchor) — short description`, grouped by source file with `## filename` headers. Goal: AI reads this file first (~100-200 tokens) for orientation, then jumps directly to the needed anchor without scanning all docs. After generating, report the number of anchors indexed and the file path. |
| "cập nhật mục lục" / "update TOC" | Regenerate `README.md` by SCANNING `<docs_dir>` (not a hardcoded list → new files appear automatically) + an endpoint list from `.bru` files in `<dirs.bruno>`. Exclude `<dirs.sources>/INDEX.md` from navigation — it is an AI-internal file, not human-facing. Use `project.name` for the title. **Preserve manual content:** read the existing README.md FIRST; only rebuild the generated parts (title, intro blockquote, navigation/sources/conventions lists, endpoint list). Any other `##` section the user wrote by hand must be kept as-is — if unsure whether a section is hand-written, keep it. Report what was regenerated and how many custom sections were preserved. |
| "liệt kê thuật ngữ\|field\|flow" / "list terms\|fields\|flows" / "show glossary" | Quick read-only index: if `<dirs.sources>/INDEX.md` exists → print its contents as-is. Else → scan `### ` headings in each `<dirs.sources>/*.md` file and list as `**<slug>** (<filename>)`. No file writes. |
| "tìm X" / "find X" | Retrieve the definition of X from `_sources/`. If `<dirs.sources>/INDEX.md` exists → read it first, locate the entry matching X by anchor slug or display name, then read only that section from the source file and return the definition. If INDEX.md absent → scan `### ` headings in `<dirs.sources>/*.md` for a match. If no match found in `_sources/`: try matching X against `.bru` filenames in `<dirs.bruno>` (fuzzy match on filename slug) and return the `docs` block if found. If still no match: say so clearly and suggest "thêm/sửa" to add the definition or "tạo index tìm kiếm" if index is missing. No file writes. |
| "sinh dashboard" / "build dashboard" / "generate dashboard" | Run `node <skill_dir>/dashboard/build.js` from project root (cwd), where `<skill_dir>` = this skill's base directory — it reads `.docswiki.yml` at cwd for `docs_dir` + `project.name` and writes a self-contained `dashboard.html` at cwd (all docs + `.bru` endpoints, search, dark mode). Overrides: `--docs=<dir>` `--out=<file>`. If it fails with `Cannot find module 'marked'` → run `npm install --prefix <skill_dir>/dashboard` then retry once. Report the output path and the doc/endpoint counts it prints. |

## Implicit rules (ALWAYS follow)
1. **Write source first, link second.** Adding new info → write to `<dirs.sources>`/`<dirs.bruno>` FIRST, then link from derived docs. NEVER copy a definition into a derived doc.
2. **Anchor per `lang.anchor`, content per `lang.content`** (default EN/VI). See `references/reference-conventions.md`.
3. **Run consistency check only when requested** — do not auto-run after every edit.
4. **`.bru` files in `<dirs.bruno>` are the API source of truth** — hand-authored with `docs` blocks. The complete HTML docs is generated by Bruno on demand (GUI "Generate Documentation") and is NOT committed to the repo.
5. **Read INDEX.md before searching docs.** When answering any question about project concepts, terms, fields, flows, or decisions: if `<dirs.sources>/INDEX.md` exists → read it FIRST (~100-200 tokens) to locate the exact anchor, then read ONLY that section. Do NOT scan all `<dirs.sources>/` files unless INDEX.md is absent.
6. **Docs mention without explicit command** → ask in the user's language before acting.
   Present a numbered-choice question so the user can reply with a number or type freely.
   Example (adapt to user's language):
   "I see you're working with docs. What would you like to do?
   1. Use **docs-wiki** — init structure, add/edit terms/fields/flows/endpoints, restructure, check consistency, generate Bruno, etc.
   2. Just answer my question — no docs-wiki needed
   3. Other (describe what you need)"
   If user picks 2 or their answer doesn't need docs-wiki → exit this skill and proceed normally.
